# 構成とネイティブクライアントへの拡張

花札館は、Rust のゲームサーバーと Web クライアントを分けた構成です。カードの配布、手番、取り札、役、得点、CPU の判断はサーバーで処理します。クライアントは操作を送信し、受け取った状態を描画します。

```text
Web クライアント（React / TypeScript）
  ├─ REST: ゲストセッション、部屋一覧、作成、入室
  └─ WebSocket: ゲーム操作、個別の状態通知、チャット
                         │
                  Rust / Axum サーバー
                  ├─ セッション・部屋管理
                  ├─ こいこいルール・CPU
                  └─ Web の静的ファイル配信
```

開発時は Vite が `/api` を Rust サーバーへプロキシします。本番では Rust がビルド済み Web クライアントも配信するため、同じオリジンで REST と WebSocket を利用できます。

## 状態と接続

サーバーは配られた全札を保持しますが、プレイヤーに送る状態にはそのプレイヤーの手札だけを含めます。対戦相手の手札は枚数として扱い、観戦者に非公開の手札を送りません。クライアントの操作はサーバーで手番と合法性を検証します。

ゲストセッションの Bearer トークンを REST に使用し、WebSocket 接続時にもセッションと部屋の所属を確認します。部屋のパスワードは入室時の認証に使用します。ユーザーアカウントや管理者ログインの仕組みではありません。

部屋、対戦状態、チャット、ゲストセッションはメモリ上にあります。プロセスを再起動すると失われます。現状はサーバー 1 プロセスでの運用を前提とし、複数インスタンスへリクエストを分散する構成には対応していません。

## ネイティブアプリを追加するとき

ネイティブアプリも同じ [REST / WebSocket API](api.md) を利用できます。UI や GPU 描画、効果音を各プラットフォームで実装し、ゲームの判定をサーバーに残すことで、Web と同じ部屋で対戦できます。

将来の拡張では、まず API にバージョンを付け、JSON メッセージの契約を共有します。トークンは OS の安全なストレージに保存し、公開接続には HTTPS / WSS を使用します。必要に応じてゲームエンジンを Rust の独立 crate に切り出せば、ルールのテストやオフライン CPU 対戦にも再利用できます。

アカウント、戦績の永続化、ランキング、複数サーバー運用は今後の追加項目です。永続化を追加する場合は SQLite / PostgreSQL などにセッション・試合記録を移し、部屋を担当するプロセスを明確にする必要があります。
